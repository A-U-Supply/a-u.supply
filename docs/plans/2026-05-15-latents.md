# Latents — private pre-release workspace

**Branch:** `plan/latents` (plan PR #277) → implementation PR #278
**Status:** shipped (v1) — Latents, slots, items, documents, threads, and the Emulsion index are live. Follow-up fixes have been merged on `master`; the `releases.latent_id` column and the v2 promotion flow remain unbuilt (see "v2" section below). Subsequent fold-watcher work in [`2026-05-17-fold-slack-watcher.md`](2026-05-17-fold-slack-watcher.md); search-page Lemmy preview in [`2026-05-16-search-lemmy-preview.md`](2026-05-16-search-lemmy-preview.md).

## Executive summary

Latents is a private, admin-only workspace for assembling pre-release works of any media type — albums, music videos, photo zines, anything in progress. Each in-progress work is a *Latent*. A Latent can be:

- Subdivided into ordered, named **slots** — per-Latent units that gather files and discussion (Track 3 of an album, Scene 5 of a video, Spread 12 of a zine). Each slot has its own status, files, notes, and a pinned "current" file per media type.
- Annotated with **multiple named documents** at the Latent level (markdown, autosaved, with revision history) for things like pre-prod checklists, art direction, mastering plans.
- Populated with **files** from a new admin-only Meilisearch index called **Emulsion** (the destination for any user upload not tied to a release) and from the existing `images`, `audio`, and `video` indices. A file can belong to any number of Latents and to any number of slots within a Latent.
- Discussed through **threaded conversation** powered by Lemmy. Threads anchor to the Latent as a whole, to a specific slot inside it, or — separately — to any single media item across the search indices. The thread layer is generic from day one.

Discussion is powered by Lemmy, an open-source platform modelled on Reddit: communities (subreddits), posts (threads), and nested comments. A Lemmy instance is being stood up at `fold.a-u.supply` for unrelated reasons; Latents reuses it. Every Latent gets its own private Lemmy community for project- and slot-anchored discussion; one additional global private community called `stacks` hosts media-item-anchored discussion across the search indices. Threads are rendered natively against our own API, which proxies all requests to Lemmy server-side. The fold instance itself serves as an optional overflow venue. Nothing is exposed publicly: communities are local-only, federation is disabled at the instance level, and visibility is scoped to authenticated admin users.

The existing Workspace concept (an ephemeral bag of media items used to feed bot jobs) is not extended. A Latent is a long-lived creative container with a status arc, slots, notes, threads, and a distinct UX; the two remain independent.

Emulsion is implemented as a fourth Meilisearch index rather than as a filter on the existing indices because user-curated project files are a different document type from scraped public media — different ownership, lifecycle, and filter surface.

Bot integration is intentionally minimal: Latents can attach media from any index (including bot outputs), but no project-aware bot pipeline is wired. Bot jobs continue to consume media through the existing Workspace flow.

Membership is flat — every admin sees every Latent.

Naming draws on photographic process language, consistent with the existing admin vocabulary (Punctum, Photism, Bullethole): a *latent image* is the chemical pattern formed on film prior to development — pure potential, not yet visible. *Emulsion* is the photo-sensitive layer in which latent images form. *Stacks* reuses the existing framing of the upload page to name the global discussion home for the search archive.

## Goal

A first-class, admin-only workspace for assembling pre-release works of any media type. Files, structured slots, notes, and threaded discussion in one view per Latent. A horizontally generic thread system that activates across the rest of the admin UI for free.

## Data model

### `projects` — a Latent

```
id                    String PK (uuid)
slug                  String UNIQUE       — URL slug; also doubles as Lemmy community slug
name                  String
kind                  String              — 'album' | 'video' | 'zine' | 'other'
status                String              — 'forming' | 'developing' | 'fixing' | 'abandoned'
hero_media_item_id    String FK media_items.id NULL  — explicit override; null falls back to first attached image
lemmy_community_id    Integer NULL        — populated on first sync
created_by            Integer FK users.id
created_at            DateTime
updated_at            DateTime
```

Status arc: `forming → developing → fixing`, plus `abandoned` as a sideways terminal state reachable from any point. No `archived`, no `done`. Status changes never lock edits — they are labels for sorting and triage.

`kind` drives slot auto-labeling only. It does not change page layout in v1.

### `project_slots`

Ordered, named subdivisions of a Latent. Optional — a Latent can have zero slots and hold only loose files.

```
id              String PK (uuid)
project_id      String FK projects.id ON DELETE CASCADE
position        Integer             — ordering within the Latent
label           String              — user-editable; auto-set on creation based on parent's kind
notes           Text NULL           — single per-slot notes block (markdown)
notes_updated_at DateTime NULL
status          String              — 'forming' | 'developing' | 'fixed'
created_at      DateTime
updated_at      DateTime
```

Slot label defaults on creation:

| `projects.kind` | Default slot label |
|---|---|
| `album` | `Track N` |
| `video` | `Scene N` |
| `zine` | `Spread N` |
| `other` | `Part N` |

`N` is the next free position. Users rename freely.

### `slot_primary_pins`

Per slot, per media type, the file pinned as the slot's current "primary" for at-a-glance views. A slot can have at most one pinned image, one pinned audio, one pinned video, and one pinned session. Pinning is independent of attachment — every attached file remains visible as a peer.

```
slot_id        String FK project_slots.id ON DELETE CASCADE
media_type     String              — 'image' | 'audio' | 'video' | 'session'
media_item_id  String FK media_items.id ON DELETE CASCADE
PRIMARY KEY (slot_id, media_type)
```

### `project_items` — many-to-many `projects` ↔ `media_items`

```
id              String PK (uuid)
project_id      String FK projects.id ON DELETE CASCADE
slot_id         String FK project_slots.id ON DELETE SET NULL NULL
                  — null = file is attached at the Latent level (loose)
media_item_id   String FK media_items.id ON DELETE CASCADE
added_by        Integer FK users.id
added_at        DateTime
UNIQUE(project_id, slot_id, media_item_id)
```

A media item can belong to many projects and many slots. Detaching from a slot does not delete the row; it sets `slot_id` to null so the file remains attached at the loose level.

### `project_documents`

Multiple named markdown documents per Latent.

```
id              String PK (uuid)
project_id      String FK projects.id ON DELETE CASCADE
position        Integer             — ordering in the documents strip
name            String              — user-editable title
content         Text                — markdown body
updated_by      Integer FK users.id
updated_at      DateTime
created_at      DateTime
```

New Latents start with zero documents. The band creates them as needed.

### `project_document_revisions`

```
id              String PK (uuid)
document_id     String FK project_documents.id ON DELETE CASCADE
content         Text                — full snapshot, not a diff
saved_by        Integer FK users.id
saved_at        DateTime
```

Snapshot on every autosave that materially differs from the previous one. Capped retention by row count (last 100 per document).

### `threads` — generic discussion anchor

A single horizontally-shared table backing all in-UI threading. Anchors to projects, slots, and media items in v1; extensible to other entity types later without schema change.

```
id                  String PK (uuid)
anchor_type         String          — 'project' | 'slot' | 'media_item'
anchor_id           String          — id in the corresponding table
lemmy_post_id       Integer
lemmy_community_id  Integer         — denormalised for fast routing
created_by          Integer FK users.id
created_at          DateTime
INDEX (anchor_type, anchor_id)
```

Anchor routing:

| `anchor_type` | Lives in Lemmy community |
|---|---|
| `project` | The Latent's own community |
| `slot` | The parent Latent's community (slot association is our-side metadata only) |
| `media_item` | The global `stacks` community |

Comments are not stored on our side — they live entirely on Lemmy, fetched on demand through the proxy endpoints.

### `media_session_meta`

DAW and NLE project files are a first-class media type alongside image / audio / video. This table parallels the existing per-type metadata tables (`media_audio_meta`, `media_image_meta`, `media_video_meta`).

```
media_item_id        String PK FK media_items.id ON DELETE CASCADE
tool                 String           — 'logic' | 'ableton' | 'reaper' | 'protools' | 'flstudio' | 'bitwig'
                                      | 'premiere' | 'davinci' | 'finalcut' | 'aftereffects'
                                      | 'lightroom' | 'captureone' | 'photoshop' | 'other'
tool_version         String NULL      — best-effort, parsed from bundle if available
original_bundle_name String           — original filename incl. extension (e.g. "Heliotrope_mix7.logicx")
bundle_size_bytes    Integer
notes                Text NULL        — optional user note ("post-mastering revision", etc.)
```

macOS bundles (`.logicx`, `.als` is single-file; `.ptx`, `.fcpbundle`, `.aep` vary) are zipped client-side before upload to ensure a single-file transfer.

`media_items.media_type` accepts a fourth value, `session`, in addition to the existing `image` / `audio` / `video`.

### Changes to existing tables

- `users.lemmy_user_id` `Integer NULL` — populated on first Latent or search-thread access.
- `users.lemmy_token_encrypted` `Text NULL` — encrypted Lemmy JWT.
- `media_items.media_type` — value set widens to include `session`.
- `releases.latent_id` `String FK projects.id NULL` — reserved column for the v2 Latent → Release promotion flow. Always null in v1; no UI surfaces it. Adding it now removes a migration step later. See the v2 section below.

No structural changes to `media_sources` or `workspaces`. Workspace and Latent remain independent. Slot pinned audio already uses `media_item_id`, which is the same identifier `Track` rows reference — no schema work needed to make v2 promotion line up.

## Emulsion — the new search index

Fourth Meilisearch index alongside `images`, `audio`, `video`:

- **Name:** `emulsion`
- **Contents:** media items uploaded by admin users, not scraped from public sources and not part of a release.
- **Document shape:** same schema as the existing indices, plus a filterable `project_ids: []` array so a single file is reachable via any Latent it belongs to. Documents carry a `media_type` field with values `image | audio | video | session`. The `session` type covers DAW and NLE project files (Logic, Ableton, Reaper, Pro Tools, FL, Bitwig; Premiere, DaVinci, Final Cut, After Effects; Lightroom, Capture One, Photoshop) with metadata in `media_session_meta`.
- **Routing on upload:** the unified `<Uploader />` Svelte component posts to the upload API with `destination='emulsion'`. The upload pipeline writes the `MediaItem` and indexes into Emulsion regardless of media type. Image, audio, video, and session files uploaded by users go to Emulsion — not into `images`/`audio`/`video`. Those existing indices remain scoped to scraped public media and release-tied media.
- **Cross-index attachment:** the Latent page's "Pull from index" modal searches all four indices. Attaching a media item from any index writes a `project_items` row and updates the corresponding doc's `project_ids` array.

`INDEX_NAMES` in `server/search_client.py` grows to `{"image": "images", "audio": "audio", "video": "video", "emulsion": "emulsion"}`.

## Lemmy integration

### Communities

| Community | Purpose | Created |
|---|---|---|
| One per Latent, slug-matched | Hosts `project` and `slot` threads for that Latent | Automatically on Latent creation |
| Global `stacks` community | Hosts `media_item` threads for any search doc | Auto-created on first search-thread access if not present |

All communities use `visibility: LocalOnly` (Lemmy 0.19+). Federation is additionally disabled at the fold instance level for redundancy.

### Identity and auth

- Each au-supply admin user gets a 1:1 Lemmy account, auto-provisioned via the Lemmy admin API on first Latent or search-thread access.
- Server-generated random password; band members never need to log into fold directly.
- The Lemmy JWT returned on login is stored encrypted in `users.lemmy_token_encrypted`. JWT lifetime is configurable on Lemmy — set long, refresh on expiry.
- The browser never talks to fold. All Lemmy reads and writes go through new FastAPI endpoints on a-u.supply that proxy to Lemmy using the calling user's token.

### Auto-provisioning sequence

1. User opens a Latent or search-doc detail page for the first time.
2. Backend checks `users.lemmy_user_id`. If null, provision the user via Lemmy admin API and authenticate to capture a JWT.
3. Backend checks the target community:
   - For a Latent: `projects.lemmy_community_id`. If null, create a new local-only community with the project's slug, the calling user as first mod.
   - For `stacks`: ensure the global community exists (cached in server config or a singleton row).
4. Subsequent visits skip both steps.

All checks are idempotent and re-entrant on failure.

### Outage degradation

- **Latent and search-doc pages**: files, slots, and documents continue to work if Lemmy is down. The Threads section renders an inline "discussion temporarily unavailable" banner with retry.
- **Latent creation**: if Lemmy is unreachable, the Latent is still created (`lemmy_community_id` left null); a background job retries community provisioning. The Threads section shows a "discussion provisioning" state until the community lands.

### Voting

Vote controls are hidden everywhere in our UI. Lemmy itself still tracks them internally; we do not surface them.

## API surface (a-u.supply)

### Projects, slots, documents, items

```
GET    /api/projects                                     → list (filter: status, kind, created_by)
POST   /api/projects                                     → create { name, kind }
GET    /api/projects/:id                                 → header + slots summary + documents summary
PATCH  /api/projects/:id                                 → update name, kind, status, hero_media_item_id
DELETE /api/projects/:id                                 → hard delete

GET    /api/projects/:id/slots                           → list slots in order
POST   /api/projects/:id/slots                           → create { label?, position? }; auto-labels if omitted
PATCH  /api/projects/:id/slots/:slot_id                  → rename, change status, update notes
DELETE /api/projects/:id/slots/:slot_id                  → delete (attached items demote to loose)
POST   /api/projects/:id/slots/reorder                   → bulk reorder

PUT    /api/projects/:id/slots/:slot_id/pin              → { media_type, media_item_id }
DELETE /api/projects/:id/slots/:slot_id/pin/:media_type  → clear pin

GET    /api/projects/:id/items                           → list attached media items, joined; includes slot_id
POST   /api/projects/:id/items                           → attach { media_item_ids: [], slot_id? }
PATCH  /api/projects/:id/items/:item_id                  → move between slots, or to loose
DELETE /api/projects/:id/items/:item_id                  → detach

GET    /api/projects/:id/documents                       → list (header + position)
POST   /api/projects/:id/documents                       → create { name }
GET    /api/projects/:id/documents/:doc_id               → full content
PATCH  /api/projects/:id/documents/:doc_id               → rename or update content (writes revision)
DELETE /api/projects/:id/documents/:doc_id               → delete
GET    /api/projects/:id/documents/:doc_id/revisions     → revision history
POST   /api/projects/:id/documents/reorder               → bulk reorder
```

### Threads — generic, anchor-typed

The same endpoints serve `project`, `slot`, and `media_item` anchors.

```
GET    /api/threads?anchor_type=...&anchor_id=...        → list threads for an anchor
POST   /api/threads                                      → create { anchor_type, anchor_id, title, body, url? }
                                                            url enables link-post preview (Lemmy fetches og data)
GET    /api/threads/:id                                  → thread + nested comments
POST   /api/threads/:id/comments                         → reply { body, parent_comment_id? }
PATCH  /api/threads/:id                                  → edit own thread
PATCH  /api/threads/:id/comments/:comment_id             → edit own comment
DELETE /api/threads/:id, /api/threads/:id/comments/:cid
```

Each call resolves anchor → community → Lemmy post or comment, loads the caller's Lemmy token, calls Lemmy, normalises the response, and returns. Lemmy errors degrade to clean UI messages rather than 500s.

### Upload extension

`POST /api/media/upload` gains optional `project_id` and `slot_id` parameters. When `project_id` is set: route to Emulsion, auto-attach to the project (and slot, if provided), and update the doc's `project_ids` array.

## Out of scope (deferred)

- **Real-time collaborative editing.** Single-author markdown with autosave and revision history only. Yjs / TipTap reconsidered only if writers actually step on each other.
- **Latent → Release promotion.** Latents and Releases are entirely separate worlds in v1. The reserved `releases.latent_id` column ships unused; planned v2 shape is described in the section below.
- **Generic non-media file types in Emulsion** (PDFs, plain-text lyric files, mood-board PDFs). DAW and NLE project files are first-class as the `session` media type — see data model. Lyric drafts live in slot notes or Latent documents.
- **Orphan-file garbage collection** when a Latent is deleted. Out of scope; its own plan later.
- **Per-Latent membership / access control.** Flat for v1.
- **Bot pipeline awareness of Latents.** Latents can attach any media item from any index, but jobs carry no project lineage.
- **Canonical thread templates.** Start ad-hoc; revisit auto-creating "General / Lyrics / Art Direction / Mix Notes" stubs later.
- **OIDC SSO** between a-u.supply and fold.
- **Mobile-specific UX polish.** Desktop is primary for v1; mobile must function but is not optimised.
- **Per-Latent custom fields** (producer, engineer, studio, target date). Use documents and notes for v1.

## v2 — Latent → Release promotion

Not built in v1. Sketched here so the v1 schema doesn't paint us into a corner and so the shape is documented when we're ready to ship it.

### Trigger

A "Promote to Release" action on the Latent detail page, available once the Latent's status is `fixing` (or at any time — soft gate, not hard). Opens a form pre-filled from the Latent (name → release title, slots → tracks, hero → cover art).

### What happens on promote

1. A new `Release` row is created with `latent_id` set to the source Latent's id.
2. For `kind=album` Latents: each slot maps 1:1 to a release `Track`. Slot label → track title, slot `position` → track number, slot's pinned audio → track audio (see below).
3. Other Latent kinds (`video`, `zine`, `other`) have less obvious mappings to existing release shapes; their promotion flow is designed when the first real case shows up.

### Share vs. copy semantics

- **Most attached media items** (cover art, supporting images, video clips referenced from the release page) are **shared** — the release references the same `media_item_id` rows the Latent does. One file, one row. Saves storage; aligns with how the rest of the site handles media reuse.
- **Final audio masters** are **copied** at promote time. The slot's pinned audio is duplicated from Emulsion into the public `audio` index as a new `media_item`, and the new `Track` row references that copy. This snapshots the release at promote time — a later re-bounce in the Latent does not silently change what's public.
- **Project files (`session` media type) are never promoted to a public release.** They stay in Emulsion attached to the Latent.

### Where release-grade media lives

- Public release audio always lives in the `audio` index post-promote, not in Emulsion. Same goes for any image used as release cover art (copied into `images`).
- Emulsion remains the pre-release WIP pool. Nothing in the public catalog ever references Emulsion directly.

### Reverse linkage

- `releases.latent_id` lets the catalog admin UI show "originated from Latent: X" on a release detail page.
- The source Latent can show "Released as: X" on its header, with a link back to the catalog entry.
- After promotion the Latent is *not* archived or locked. The band may continue editing notes, threads, slots — that's now post-release history.

### Status interaction

- The Latent's status does not change automatically on promote. The band can choose to keep working in the Latent (now post-release) or manually mark slots `fixed` to signal closure. No new status value is added.
- A Latent can in principle be promoted again (re-release / remaster) — the second `Release` row also points back via `latent_id`. The reverse-linkage UI on the Latent shows the most recent release prominently and links to prior releases below.

### Out of scope even for v2

- Unpublishing a release back to draft Latent state.
- Multi-Latent → one-Release composition (compilations spanning several Latents).
- Automatic Latent status transitions on promote.

## Open questions

1. **Lemmy admin token storage.** Server needs a long-lived admin token to provision users and create communities. Stored as `LEMMY_ADMIN_TOKEN` env var on Dokku?
2. **Lemmy version on fold.** Confirm 0.19+ so `visibility: LocalOnly` is available. Fallback if older is federation-disabled-at-instance only.
3. **Lemmy user mapping.** Login must be unique and ASCII-safe. Proposed: login = slug from `users.email`, display name = `users.name`. Confirm.
4. **Sidebar real estate.** Adding "Latents" makes a sixth top-level section (Search, Atelier, Catalog, Jobs, Bookmarks, Latents). Append, or rethink grouping?
5. **`kind` values.** Current set: `album` | `video` | `zine` | `other`. Any additional primary kinds for day one (e.g. `mixtape`, `single`, `live-set`)? `other` is the safety valve.
